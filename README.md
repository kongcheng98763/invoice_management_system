# invoice_management_system

> ## 开发中，功能尚不完整
>
> 目前实现了：火车票票面字段提取；电子发票（普通发票、增值税专用发票）的开票日期、发票号码、项目明细、购销方、价税合计与备注提取；多页 PDF 的逐页解析与跨页换行拼接；按票种收集 PDF；给界面用的本地 FastAPI 服务；界面侧的目录扫描与**把微信／资源管理器里的文件拖进放置框**收集。
> 还没落地：SQLite 台账、归档目录与报销表的对账。`winui\` 前端已能编译并跑通发票识别页（自包含方式，见第五节），台账页和首页统计还是占位。
> 函数签名和返回的 dict 结构都可能随开发变动，引用前请先看代码确认。
> 两条口径限制要先看：**一份 PDF 只按一张票解析**（合并多张会串字段，页码对不上时会给告警），`invoice_date` 在火车票上是行程日期、在普票/专票上才是开票日期。

[English documentation](README.en.md)

用 pdfplumber 从发票 PDF 中读出票面关键字段。**仅支持 Windows**，未在其他系统验证过。
- **单页提取函数以 `page` 为入参**，多页票用 `extract_invoice_regular_pages(pages)` / `extract_invoice_VAT_pages(pages)` 逐页解析并把跨页换行的项目名称拼回去。

## 三、提取脚本

提取函数共用同一套流程：`page.extract_text()` 取整页文字 → `unicodedata.normalize("NFKC", text)` 归一化 → 逐行正则匹配字段，版式固定且文字粘连的区域改用 `page.crop(box)` 单独取词。

裁剪一律带 `strict=False`：pdfplumber 默认要求裁剪框完全落在页面内，而实测 674 页样本里有 136 页的表格格子画出页边（火车票版式最典型，`y0 = -0.002` 这种零点几毫米的越界），默认口径会直接抛 `ValueError`——走到扫描管线里就是「类别都判出来了却标成无法解析、不归档」。夹回页面范围不影响文字，票面内容本来就在页面里。

归一化：PDF 抽出的汉字常是部首兼容字（如 `⼦` U+2FBA），不还原成 `子` U+5B50，正则一定匹配不上。

### `train_invoice_recognition.py`

`extract_invoice_train(page)`：提取火车票（电子客票）票面字段。入参为 `pdfplumber.Page`，返回 `dict`。

| 键 | 含义 | 备注 |
|---|---|---|
| `is_train` | 是否为火车票 | 在标题裁剪框 `(89, 8, (418 + page.width) / 2, 38)` 内匹配「电子发票（铁路电子客票）」；为 `False` 时返回的 dict **只含这一个键**，调用方必须先判此键再分流 |
| `e_ticket_number` | 电子客票号 | 「电子客票号」后紧跟的 25 位 |
| `state` | 客票状态 | 紧跟客票号的文字，如 `退票`／`补票`／`始发改签`；没有则为 `None` |
| `invoice_no` | 发票号码 | 8–20 位，兼容 `发票号码` 与 `No.` 两种前缀 |
| `invoice_date` / `invoice_time` | 行程日期 / 发车时间 | 如 `2026年04月17日` + `11:54` |
| `total_amount` | 价税合计（小写） | 如 `39.00`；票面上的 `¥` 已去掉，货币符号由界面补，跨票种保持同一形态 |
| `id` / `person` | 脱敏身份证号 / 乘车人姓名 | 身份证形如 `1234567890****123X` |
| `site` | `[起点站, 终点站]` | 由两个固定裁剪框各取首行；坐标按手头样本票量得，票样版式变了要重新测。裁剪框取空时会记一条「站点信息提取失败」告警并提前返回（判空必须在补成 `""` 之前，否则这条告警永远走不到） |

注意事项：

- 三条取文路径并存：`is_train` 用标题裁剪框，`e_ticket_number`/`state` 用 `extract_text(use_text_flow=True)` 的流式文本，其余字段用默认阅读顺序的文本；都要先 NFKC 归一化。
- 日期时间提取失败时函数**提前返回半成品 dict**，其后的键可能缺失或为 `None`，不能假设键齐全。
- 失败提示统一走 `invoice_item_recognition.warn()`：只把消息攒进告警清单，不弹窗，怎么展示由上层决定。

### `regular_invoice_recognition.py`

`extract_invoice_regular(page)`：判断是否电子发票（普通发票），是则再取开票日期、发票号码和 `invoice_item_recognition` 的那套票面字段。返回 `dict`。多页用 `extract_invoice_regular_pages(pages)`。

| 键 | 含义 | 备注 |
|---|---|---|
| `is_regular` | 是否普通发票 | 在标题裁剪框 `(128, 10, 416, 49)` 内匹配「电子发票（普通发票）」，括号全角半角都兼容；为 `False` 时**只返回这一个键** |
| `invoice_date` | 开票日期 | 票头裁剪框 `(432, 17, page.width, 69)` 内匹配 `开票日期：2026年9月2日` |
| `invoice_number` | 发票号码 | 同一裁剪框内匹配 20 位数字 |
| 其余键 | 项目明细、购销方、价税合计、备注等 | 见下面 `invoice_item_recognition.py` |

注意事项：

- `is_regular` 为 `False` 时不会走到日期/号码那一步，调用方需先判此键。
- 日期或号码没匹配到时对应值为 `None`，同时记一条告警（不抛异常、不中断扫描）。
- 标题措辞变化或新增票种都要扩规则。

### `invoice_item_recognition.py`

电子发票（普通发票）和电子发票（增值税专用发票）的项目明细区版式相同，解析集中在这一个模块，两个票种模块都调它。

`extract_invoice_item_fields(page)`：解析单页；`extract_invoice_items(pages)`：解析整份 PDF，负责跨页拼接。

| 键 | 含义 | 备注 |
|---|---|---|
| `item_list` / `records` | 项目明细 | 每条八个栏目：`item_name` `spec` `unit` `quantity` `unit_price` `amount` `tax_rate` `tax_amount`；票面没有的栏给空串。`records` 是单页的中间结果 `[("row", InvoiceItem) / ("frag", {...})]`，汇总函数已把它消化掉 |
| `buyer` / `seller` | 购买方 / 销售方 | `{"name","tax_id"}`；取主表第一行的第二格和**最后一格**——普票第一行有合并格、专票没有，取最后一格两种票就统一了 |
| `remark` | 备注 | 首格写成「备 注」的那一行：把空白去掉后，开头三个字以内出现「备注」就算（机票票样里上排的「姓」会被合并格挤成「姓 备 注」），整串里才含「备」「注」的项目名（备用件、注塑件）不算；多页按页序拼接 |
| `total_upper` / `total_amount` | 价税合计大写 / 小写 | 小写不带 `¥`，只认到两位小数，否则去掉空白后会和后面备注里的编号连成一串 |
| `amount_total` / `tax_total` | 合计行的金额 / 税额 | 用表头实测的竖带定位 |
| `page_count` / `page_no` / `drawer` | 共X页 / 第Y页 / 开票人 | 票面没写为 `None`；`extract_invoice_items` 会盯着 `page_no` 是否递增，回到第 1 页或重复就报「像是装了不止一张票」的告警 |

注意事项：

- 认栏方式是「表头逐词累加凑栏目名 → 实测每栏横向范围 → 相邻栏中点当竖带 → 数据行的词按中心 x 落带」，金额、税率两栏都有字才算一条完整项目行，其余视为上一行的换行续排（跨页同理：`*电子元件*价外费用（配` + 下一页的 `送费）` 拼回同一条）。
- 栏位一律从表头实测、不写死坐标：票样里既有 595/600 两种页宽，也有缺「规格型号／单位」栏、单价排在数量前面、整排表头与数据错位的票。
- 有些票用重影字做假粗体（同一位置画两遍），`dedupe_page` 先去掉重画的字，否则连数字都会翻倍成 `9966..4466`。
- 表头错位时金额会被挤进税率栏得到 `96.4613%` 这种值，`realign_amount` 把它拆回金额栏。
- 不征税、免税行的税额栏本来就是空的，所以判定完整行只要求金额 + 税率两栏。
- 竖带按词的中心划分，因此一个词横跨两栏（数量、单价挤出边界）时会分错，这种票样还没遇到。
- 改判定规则要拿全量票样逐字节对比，不能只看跑通：`tempemark_snapshot.py` 把 394 条「备注 / 购销方税号」结果导出来，改前改后各导一次 diff。备注行改成「开头才算」时，第一版写成整格等于「备注」，机票票样立刻从有备注变成 `None`（那格实际是「姓 备 注」），放宽到开头三个字以内才做到 394 条零差异。

### `VAT_invoice_recognition.py`

`extract_invoice_VAT(page)`：判断是否电子发票（增值税专用发票），是则再取开票日期、发票号码和 `invoice_item_recognition` 的那套票面字段。返回 `dict`。多页用 `extract_invoice_VAT_pages(pages)`。

| 键 | 含义 | 备注 |
|---|---|---|
| `is_vat` | 是否增值税专用发票 | 在标题裁剪框 `(121, 14, 432, 52)` 内匹配「电子发票（增值税专用发票）」；为 `False` 时**只返回这一个键** |
| `invoice_date` / `invoice_number` | 开票日期 / 发票号码 | 先按票头裁剪框取；专票样本里标签和值常被印章隔开，取不到就退回整页认年月日和 20 位号码 |
| 其余键 | 项目明细、购销方、价税合计、备注等 | 见上面 `invoice_item_recognition.py` |

注意事项：

- 整页兜底认号码用的是「连续 20 位数字」，备注里若出现同长度的号串会认错。
- 原来的三合一 `type` 判据已拆成 `is_regular` / `is_vat` 两个模块，`normal_invoice_recognition.py`（「电子发票」字样筛查）也已删除，那道筛查现在内置在 `classify_invoices.py` 的 `ELECTRONIC_INVOICE_RE`。

### `classify_invoices.py`

收集器：选一个文件夹后递归扫描其中的 PDF，按第一页判定票种，把**副本**（原件不动）复制到 `invoice_recognition/temp/发票分类/` 下。目录结构：

```
发票分类/
├── 火车票/
│   └── 多页文件/
├── 增值税发票/
│   └── 多页文件/
├── 普通发票/
│   └── 多页文件/
└── 其他发票/
    └── 多页文件/
```

分类顺序：先用 `ELECTRONIC_INVOICE_RE`（整页逐行匹配「电子发票」字样）作总开关筛掉无关 PDF，再依次问 `is_train` → 火车票、`is_vat` → 增值税发票、`is_regular` → 普通发票，过筛但三种都不匹配的归其他发票。没过筛的文件不复制，只在日志里列出。多页 PDF 归到所属类别的 `多页文件` 子文件夹；重名文件自动追加 `(1)(2)`。

注意事项：

- 扫描跑在后台线程里，日志经队列回投；主线程被逐个 PDF 阻塞时窗口拖动会变成「未响应」。
- 提取函数的告警在扫描期间只攒清单不弹窗（后台线程不能调 Tk，逐个对话框也会卡死），扫描收尾时由 `_summarise` 把清单写进日志并只弹一个汇总框。
- 打不开的 PDF 归入「无法解析」，同样不复制。
- pdfminer 对缺 `FontBBox` 的字体逐条告警（`Could not get FontBBox …`），实测不影响文字抽取，只有一条 `_QuietFontBBox` 过滤器消掉这类噪音。
- 复制归档由 `_COPY_LOCK` 串起来：tkinter 窗口和服务可能同时往同一个目录复制，重名检测（`unique_path`）不锁住就会撞在同一个 `(1)` 上。
- `find_pdfs` 会把归档目录本身（以及默认归档目录）从扫描范围里排除掉，否则第二次扫描会把上一次复制出去的副本再认一遍。
- `collect(search_root, out_dir, report, with_fields=False, files=None)` 返回五元组 `(各类数量, 多页数, 非电子发票, 无法解析, 扫描明细)`，扫描明细每项是 `{file, category, is_multi_page, note, fields}`；`with_fields=True` 才顺带逐页解析票面字段（服务侧要用），tkinter 窗口维持只分类不解析，扫描更快。`files` 是给界面拖放用的：传一组文件路径就只处理这批文件，传 `None` 或空列表才递归扫 `search_root`。

## 四、本地服务 `invoice_service.py`

need.md 3.1 的方案 A：Python 侧常驻 FastAPI，WinUI3 通过 REST + WebSocket 与它通信。

```powershell
cd invoice_recognition
uv run uvicorn invoice_service:app --host 127.0.0.1 --port 8765
```

| 端点 | 作用 |
|---|---|
| `GET /health` | 回 `{status, out_dir, categories}` |
| `POST /invoices/classify` `{"folder": 绝对路径, "files": [文件路径…]}` | 走 `collect()` 扫描归档（同样只复制、不动原件），响应是一份 `ClassifyReport`；扫描过程中日志逐行经 `/ws` 推给界面。`files` 非空时只处理这批文件（界面拖进来的场景），为空才递归扫 `folder`；两者都给不出可用目标时回 400 |
| `WS /ws` | 推送信封 `{"kind":"log","line":…}` 和 `{"kind":"done","report":…}` |
| `GET /invoices/classify/result` | 501 占位，等台账落地再实现 |

注意事项：

- 拖放那条链路（`collect(..., files=[…])`）由 `temp\files_protocol_test.py` 回归，14 例，重点是「只复制不动原件」这条硬约束——扫完一遍后逐个比对原件的大小与 mtime/ctime 必须完全不变；另外还管重名不覆盖旧副本、空清单退回整目录扫、归档目录里已有的副本不再被复制第二遍、管道／设备名当场挡下，以及单次上限：`MAX_FILES`（服务）和 `DropInbox.MaxFiles`（界面）这两个数字必须一致（用例直接读两边源码，改一处忘另一处会当场报出），超上限的请求整批 400 拒绝**且归档目录里一个副本都不许多出来**，正好在上限内的不因数量被拒、也不写出副本。后两例是**打真服务**的，所以用例会先校验那个服务的 `out_dir` 落在仓库 `temp\` 下面（`temp\restart_service.ps1 -OutDir <temp 下的绝对路径>`）——本进程 import 时设的环境变量管不到已经在跑的那个进程，指回默认归档时它就会往正式归档里写副本，所以不满足就直接判失败。
- 服务只绑 `127.0.0.1` 且不做鉴权：客户端给什么绝对路径它就去读、并复制进归档目录。这是「单人本机、界面是唯一调用方」前提下的取舍，别把它监听到大网口上给别人用。
- 畸形路径实测都归入「无法解析」而不是 500：不存在、拖走后被删、保留设备名 `C:\con.pdf`、UNC 共享、不存在的盘符、相对路径都只影响那一条记录；微信风格的超长中文带空格全角括号文件名能正常归档。
- 归档固定在 `invoice_recognition\temp\发票分类`；设环境变量 `INVOICE_OUT_DIR` 可以指到别处试跑，免得往正式归档目录里堆副本。
- 扫描跑在 `asyncio.to_thread` 的工作线程里，日志要回投事件循环才能发给界面，所以广播器存了启动时的 loop。
- 一次只跑一个扫描（`_scan_lock`）：告警清单、归档目录和 WebSocket 广播都是进程级共享的，并发跑会互相串日志、也会撞重名文件。
- 已知没修的（单人本机场景下代价可接受，别照着上多用户）：WebSocket 广播不分会话，开两个窗口会互相看到对方的日志和「扫描完成」；`_COPY_LOCK` 只在进程内有效，同时开 tkinter 和两份服务仍可能撞副本重名；拖放去重按字符串比较，同一文件的短名/UNC/junction 另一种写法会被算成两个。
- 已修：微信一次只能拖一个文件，逐张连拖时清单原来**每次被整批替换**，只有最后拖的那张会被归档（界面数字看着正常，静默漏档）。现在按路径累加去重，提示报「累计 N 个（本轮新增 M 个）」；`_dropSeq` 判废那条以前零反馈（枚举大目录要几秒，期间用户改目录或点清除，这次拖放就人间蒸发），现在提示和日志都会写「作废」和原因。
- 拖放链路审查查出的四条，现在都按本机实测处理完了（① ② ③ 已修，④ 那条前提在这台机器上不成立）：① 只拖**一个文件夹**走早退分支，「文件夹根本读不动」原来两侧都静默吞掉（实测 `C:\Documents and Settings` → `isdir=True`、`walk_files` 产出 0 条 → HTTP 200、counts 全 0，界面写「已归档 0 个发票」，用户以为里面没票；同一个文件夹**多带一张 jpg** 就会走客户端枚举、那时才会明说「拒绝访问」，两种拖法不对称）。现在界面侧早退之前先 `ProbeReadable` 试列一次根目录，读不动当场写「拖进来的文件夹读不动：…」；服务侧 `walk_files` 把 `scandir` 的 `PermissionError` 通过回调交给 `collect`，日志逐条报「[目录读不动，已跳过] 路径：原因」，最多列 5 条再多一句「另有 N 个目录没读」。两侧由 `temp\denied_dir_probe.py`（`icacls /deny` 现造拒读目录，6 例）和 `temp\dropinbox_test` 那条「只拖一个读不动的文件夹」盯着。
- ② `ReadDroppedPathsAsync` 原来把 `try` 包住整个 `foreach`：某项取路径抛异常时，已收到的残缺清单被当成全部，而且 `paths.Count > 0` 会跳过文本兜底——少收了没人说。现在「逐项取路径」集中到 `DropInbox.CollectPaths`（每项传成一个委托，真正的跨进程调用发生在被问的那一刻），坏一项只丢那一项并计入 `LostItems`，界面据此单起一行「注意：这次拖进来的文件清单里有 N 项取不到路径（清单里认出 X 项，加上文本兜底一共 Y 项）」，有坏项时文本兜底照走；来源给了空路径（回收站、还没落盘的云端占位）同样算坏项，不会以空串混进清单。`temp\dropinbox_test` 直接编这份生产代码验 5 例（全好／中间一项抛／整批都抛／空路径／一个项都没给）。文本兜底并进来之前按忽略大小写去重，这一步抽成了 `DropInbox.MergeTextFallback`（纯函数，harness 里 5 例：文本重复清单那项、大小写不同、`file://` 形式、清单空、文本整段空白，最后一例直接断言「目录在两种格式里各出现一次时仍然按『只拖一个文件夹』处理」）——文本里常常又带着清单已给过的那几项，重复的一项会让早退失效（同一目录被数成两个，于是改走 `files` 清单、撞上 2000 上限、源目录框也不会被填上）；`await view.GetTextAsync()` 自己包了一层 try，数据对象已释放时它会抛，不接住就冒出这个方法、上层整批丢掉，连已经拿到的那几项也没了（表现成「拖了没反应」）；`CollectPaths` 留的是**第一个**原因（后面项的错不覆盖它），界面那句因此写「首个原因：…」；整批都是空路径时报的是「N 项都没给出可用的路径」而不是「清单读不出来」。「只拖归档副本」那一种情形的提示也改了口径：写「拖进来的 N 份都是归档目录里已有的副本，按约定不再归档第二次」，原来它写「拖进来的没有 PDF」，和同一轮日志里那句「1 个是归档目录里的副本，跳过」当面吵架。整套 harness 现在 33 例。
- ③ `_droppedFiles`、`_dropSeq` 跟着 `LiveLog` 一起改成静态：切页重建的那一页在构造函数里发现清单非空就重新声明一次「累计 N 个 PDF 待处理（切页回来清单还在），点「开始分类」处理」，并把「清除拖入」按钮显出来——不会再出现日志写着已拖入 N 个、点按钮却去扫源目录。
- ④ 评审说 `File.Exists` 对「超过 260 字符」答 false、而 `winui\app.manifest` 缺 `<longPathAware>`，微信缓存目录容易超长：**界面这一侧测不出来，但顺着它查到了真正会断的那一层——Python 服务**。`temp\longpath_manifest_probe.py` 先造出一条 461 字符的 PDF 路径（要用 `\\?\` 原样通道才建得出来；之前那版探针用普通写法建不出，才误以为本机不存在长路径），再把同一份代码编成「apphost 带声明」和「不带声明」两个 exe 对照，两边 `File.Exists`／读取／列父目录全部正常；shell 的 `SHCreateItemFromParsingName → SIGDN_FILESYSPATH` 也认这条文件，只是回吐成 8.3 短名形式（`INVOIC~1\…\电子发~1.PDF`，125 字符），而那条短名再交给 `File.Exists` 仍是 True。所以界面收下长路径没问题。可 `temp\long_path_probe.py` 把同一条 420 字符的路径发给正在跑的服务时，`os.path.exists` 当场答 `False`、回包写着「不是可读取的普通文件」——**界面收下了、服务读不到**，一张真发票被静默归进「无法解析」，用户看不出是长度卡的。根因是 CPython 不是长路径感知进程，而本机 `LongPathsEnabled=0`（.NET 的 System.IO 会自己加前缀，Python 不会）。现在 `classify_invoices.fs_path()` 在动手读之前做一次翻译，**两个档位不是一个数**：文件到 260 才换（实测 259 还能 `os.stat`、整 260 读不到），目录提前到 250 就换（`os.scandir` 要拿「目录\*」去做首次匹配，实测一条 256 字符的目录 `os.path.exists` 答 True 而 `scandir` 报「系统找不到指定的路径」，228 字符才 scandir 得动，250 取在实测的「通」与「不通」之间）。换写法是**逐条**做的（`walk_files` 对每个 entry 各问一次 `is_dir`）：只换根救不了「根很短、里面某条路径很长」那种树，实测那会整棵子树被当成「读不动」跳过。UNC 换成 `\\?\UNC\server\share`，相对路径和「盘符相对」（`C:foo`）不加前缀（原样通道只吃绝对路径，加了反而非法；让它们继续按「读不到就归无法解析」处理）。前缀还必须在两处摘掉，否则会咬掉硬约束和可读性：`_is_archive_copy` 和 `find_pdfs` 的归档目录排除都要先 `strip_verbatim` 再比（`resolve()` 会保留前缀，拿它和普通写法的 `out_dir` 比永远不相等，归档目录里一份 >260 的副本就会被再归档一次，违反「副本不再归档」）；发给界面的日志和 `note` 一律走 `shown()` 去前缀（否则 `无法解析：…` 里会冒出 `\\?\C:\…`）。**写归档那一侧也按目录档换**：`INVOICE_OUT_DIR` 指到很深的位置（或票名本身很长）时，目标路径过了 260 会让 `unique_path` 的存在检查永远答「不存在」——不但加不上 `(1)`，还会把已有副本覆盖掉，那违反「只复制、不动旧副本」。`temp\long_path_probe.py` 15 例盯着端到端：单条长路径、整目录扫描那条深处文件、归档里那份长副本、以及「回包（含日志与明细）里没有任何原样通道前缀」，外加「原件时间戳不变」这条硬约束；`temp\fs_path_edge.py` 10 例盯着边界（文件的 260 那一格、目录换成 `is_dir` 档后 scandir 打得开、前缀不被 pathlib 吃掉、正斜杠、盘符相对、短路径不动、已带前缀不重复加、UNC）。manifest 里那条 `<longPathAware>` 声明留着，但注释写明它不是这条链路的关键（只有系统 `LongPathsEnabled=1` 时它才是 Win32 那条路的必需品）。`temp\dropinbox_test` 的长路径用例也相应从「不能算成没有 PDF」升级成「必须真收进清单」（343 字符夹具，实测 `Files=1`）。
- 识别侧的两条口径限制，改动前要清楚代价：**一份 PDF 只按一张票解析**——票头字段取第一页、价税合计取最后一页，所以把多张票合并成一个 PDF（邮箱批量下载常见）时，一条记录会混着 A 票的号码和末票的金额；现有语料每份只有一个票根（`temp\corpus_recount.py` 用生产提取函数重数过：662 份里多页 14 份，其中电子发票 4 份，这 4 份逐页只认出一个发票号码；另外 10 份多页是火车票或不印这个票头的版式），验算发现不了。为此 `extract_invoice_items` 盯住了票面印的「共X页第Y页」：只要 Y 不比上一页大（回到第 1 页或重复），就记一条「这份 PDF 里像是装了不止一张票」的告警，让混票在现场露出来而不是静悄悄拼一起。另外 `invoice_date` 在火车票上是**行程日期**、在普票/专票上才是**开票日期**，同一个键两种含义，台账按「经手时间」用它会随票种漂移。
- 上面这条由 `temp\multi_page_boundary_test.py` 验：假页对象喂三种现场（页码递增不误报 / 回到第 1 页报警 / 没印页码不误报），再把全体语料的多页票跑一遍要求一条告警都不多，5 例全过。
- 票面字段挂在 `files` 的每个条目上（`entry["fields"]`），不再另外单列一份扁平的 `fields` 清单：扁平那份和条目对不上号，界面上列出来的票面行就说不清是哪张票。
- 响应里带 `warnings`（最多 50 条）和 `warning_count`（总条数），是这一轮扫描攒下的票面告警；扫描前会先清掉上一轮的残留。
- 归档目录里已有的副本单列成 `already_archived`，**不再混进 `non_invoices`**：把整个归档目录连着别的文件夹一起拖时，那些副本会被计入「非发票（未复制）」，看起来像识别失败——实际是「认出来了但按约定不重复归档」。界面汇总多一行「归档目录里的副本（不再重复归档）: N」，只在 N>0 时出现。
- `POST` 响应里的 `log` 只在**没有 WebSocket 订阅者**时才填，否则日志已经推过一遍，响应再给一份会把同一行写两遍。

## 五、WinUI3 前端 `winui\`

`MainWindow` 是 NavigationView + Frame 外壳，四个页面：首页、报销台账、发票识别、设置。发票识别页对应上面这个服务：选文件夹（或直接把文件拖进来）→ `POST invoices/classify` → 按四类展示归档结果 + 实时日志。`Services\ApiClient.cs` / `Services\WsClient.cs` 按 8765 端口和上面的端点写，地址在设置页可改。

拖放：源目录那一整格 `DropZone` 都是放置目标，资源管理器里的 PDF、或微信聊天窗口里收到的文件都可以按住拽进来，松手后提示会写明「已拖入 N 个 PDF」，再点「开始分类」。规则是——

- 只拖进**一个文件夹**：等同于选目录，走整目录递归扫描；
- 拖进文件（可多选）、或文件夹与文件混拖：文件夹会被展开成其中的 PDF，和散文件一起作为 `files` 发给服务；
- 非 `.pdf` 的散文件直接拒掉；一个 PDF 都没拿到时提示「拖进来的没有 PDF：只处理 .pdf 文件，拖文件夹会连它里面的 PDF 一起收」；
- 来源既不给文件清单也不给可认出的文本时，光标旁边直接写「这个来源没给出文件，只能收 PDF」，松手后日志还会列出它实际给了哪些数据格式——不然只看到一个禁止符号，没法判断差在哪。
- 提示文字旁边有「清除拖入」按钮，点了就退回按源目录扫描；一改源目录也会自动清掉之前拖入的清单——服务侧 `files` 是盖过 `folder` 的，不清的话拖过一次文件之后再换目录扫描，扫到的还是上次那批。
- 拖不动时有「粘贴文件」这条退路：在资源管理器或微信里 `Ctrl+C`，点这个按钮读进来。它读的是同一个 `DataPackageView`（CF_HDROP → `StorageItems`，纯文本 → `Text` 兜底），所以取路径、去重、累加、早退分支、提示文案全都和拖放走同一份代码，一行逻辑都没多写；`_droppedFiles` 的累加语义也顺带覆盖了「微信一次只能复制一个文件」那种情形。「粘贴文件」和「清除拖入」放在**单独一行**：上面那行已经有 5 个控件，再挤进来行尾那个条件显示的按钮会被裁到窗口外，用户看不见也点不到。
- 数据取用顺序是先 `StorageItems`（资源管理器、微信都给这个），拿不到再退 `Text`：文本按换行和分号拆、去掉包裹的引号、`file://` 还原成本地路径，`http` 之类和不像路径的纯文字丢掉。`StorageItems` 里**个别项**取不到路径不算整批成功：其余项照常收，日志单起一行「注意：这次拖进来的文件清单里有 N 项取不到路径（清单里认出 X 项，加上文本兜底一共 Y 项）」，同时照样再试一遍文本兜底，能补回来的补回来——半截清单冒充齐全时，界面写着「收到 3 个」而用户拖了 5 张，没人会怀疑是接收端漏的。
- 那四个拖放处理器同时挂在放置框 `DropZone` 和里面的输入框 `FolderPathBox` 上：用户最自然的落点是那个看得见的输入框，而 WinUI 对「命中的子控件没开 AllowDrop 时要不要冒泡给外层」并没有可靠保证——两种语义下这条路都走得通；处理器里统一 `e.Handled = true`，冒泡上来也不会处理第二遍（扫描中两个框的 AllowDrop 一起关掉）。
- `Drop` 里取清单是异步的，所以整段用 `e.GetDeferral()` 包住：不挂 deferral 时 WinUI 可能在我们拿到路径之前就把这次投递判完成，表现成「偶尔拖了没反应」。
- `DragOver` 每帧都要知道「这次能不能放」，而 `DataView.Contains()` 是一次跨进程询问：现在在 `DragEnter` 问一次记在 `_dragAcceptable` 里，`DragOver` 直接用（万一没收到 Enter 就退回现场问一次），`DragLeave`/`Drop` 清掉。几千项的大拖拽里，这一步原来每帧都跑两遍。那两个调用（`AvailableFormats`、`Contains`）都是跨进程问来源，来源中途释放数据对象（`RO_E_CLOSED`）就抛，而它们待在**同步**的 `DragEnter`/`DragOver` 里：异常冒出处理器就等于「拖到框上完全没反应」。现在统一走一个 `ProbeDraggable`，问不到就降级成「这次不接受」（光标旁那句拒绝理由照旧显示），日志按一次拖拽只报一遍——`DragOver` 每秒十几次，每次都写会把日志刷满。`DragOver` 现场问到的答案也记回 `_dragAcceptable`，不再每帧重问。
- `ProbeDraggable` 回的是**三态**（能放／确实没带文件／问不到），只有问到准数才锁进 `_dragAcceptable`。原来探测失败会把「不接受」锁在那条拖放的整个过程中——`_dragAcceptable` 只在 `DragLeave`/`Drop` 复位，而 `AcceptedOperation=None` 时 `Drop` 根本不会跑，那句本该说清的降级日志也没机会落地，用户只会看到光标旁一个禁止符号（评审 P2）。留 null 的话 `DragOver` 下一帧再问一次，重复探测只发生在「来源真的一直问不出」那条异常路径上；旁边那句话也按三种情形分开写。
- 展开文件夹跑在后台，回来时用户可能已经点了「清除」或改了目录，所以有一个 `_dropSeq` 计数：await 期间计数被别的行为动过，这次拖放结果就作废，不会把用户刚清掉的清单又塞回去。
- 文件夹会递归展开，父子目录一起拖、同一个文件夹拖两次都只算一份（`DropInbox` 去重），否则同一张票会被复制两遍。
- 一次拖太多会被砍：服务侧 `files` 的上限是 2000 个，超了**整批**回 400、一个都不归档，所以界面在发之前就截到 2000，提示和日志都写明「一共认出 N 个 PDF，只发前 2000 个，其余 M 个这次不发」。**保留的顺序是先用户亲手挑的散文件、再文件夹里展开的**——顺序反了就会把「专门拖进来的那几张」丢掉、留下按名字序的前一堆。
- 微信刚收到、还被微信自己写着的文件照样能拖进来：界面收得下这条路径，服务侧 `open()` 会被系统挡回来，明细逐条写「无法解析：[Errno 13] Permission denied: …」并计入「无法解析（未复制）」，不是静默归零；占用一松开，同一张票正常归档（`temp\locked_probe.ps1` 用独占句柄前后各发一次同一个路径，5 例）。
- 连着拖（微信一次只给一个文件）不会被互相顶掉：`ApplyDropAsync` 进后台前只**记** `_dropSeq`、不再 `++` 它。原来在入口顶一下计数，第二条拖放就会把第一条还在等磁盘的结果判成作废——而且日志还写着「期间改了源目录或点了清除」，那句原因对用户是凭空捏的。「作废」该由「清除」和「改源目录」这两件事自己去顶计数。
- 问格式的那两下也接住了：`DataPackageView.Contains` 是跨进程问来源，来源中途释放数据对象就抛 `RO_E_CLOSED`。悬停侧早就由 `ProbeDraggable` 兜着，读取侧（`ReadDroppedPathsAsync` 里那两次 `Contains`）原来是裸的——一抛整批拖放连已经拿到的一项都不剩，文本兜底也走不到。现在统一走 `ContainsSafe`，问不到就按「这个格式没有」处理，原因记进 `storageError` 照样写日志。
- 同一个文件的两种写法算一项：`DropInbox.Normalize` 先把路径收成同一个键（正斜杠、`.\`、结尾多的一根杠、`\\?\` 原样通道前缀），比较一律忽略大小写；`Plan` 开头 `Distinct`，`PathsFromText`／`MergeTextFallback`／累加清单都按这个键去重。不这么做会有两种表现：同一张票归档成 `xxx (1).pdf` 两份、数字虚高；以及 `C:\inv` 和 `C:\inv\` 被数成两个目录，于是「只拖一个文件夹 = 选目录」的早退失效、整目录被展开进 `files` 撞上 2000 上限。覆盖不到的是 8.3 短名（展开它要一次 Win32 调用，而 shell 只在超过 260 的目录上才回吐短名，那条路径服务侧本来就读得动）。
- 拖放的结果落到**看得见的那一页**：`Loaded` 时把这一页记进静态 `_active`，`Task.Run` 回来后交给 `_active` 去写提示、按钮和源目录框。等磁盘那段时间里用户切了页的话，原来这些写进的是已经卸掉的那一页——清单（进程级）明明收下了，界面上的数字还停在旧的，「清除拖入」也不出现。同理，订阅 `WsClient`/`ScanStateChanged` 从构造函数挪到 `Loaded`：外壳那个 Frame `CacheSize=1`，被缓存住的页再回来时构造函数不会再跑，只在 ctor 订阅的这一页就再也收不到推送、按钮停在「分类中…」、放置框的 `AllowDrop` 停在 `false`（看着就是「拖不进去」）。
- 「开始分类」的目录和清单同一时刻取：`files` 以前是 await 之后才从静态清单读的，而那五秒里源目录框还打得字，一敲键盘清单就被清掉，发出去的是「上一个目录 + 空清单」。现在进方法就 `new List<string>(_droppedFiles)` 拍一份快照，日志、校验、请求都用它；扫描期间「粘贴文件」按钮一并按住，防止粘进来的改动落在已经发出去的那一轮上。
- 服务没回传归档目录时，`DefaultArchiveDir` 的判据改成「哪个祖先目录里放着 `invoice_recognition`」而不是「`发票分类` 建出来了没有」：第一次跑的时候那个目录还不存在，走到的兜底是一条**相对**路径，`UnderAny` 按进程当前目录去解释它，于是「归档里的副本不再归档」这条排除静默匹配不到任何东西（归档目录里的文件吃掉 2000 的额度，那句「N 个是归档目录里的副本」也永远不出现）。
- 两条路的覆盖率不单调，这是取舍不是 bug：只拖**一个文件夹**走服务侧整目录递归，服务对 `folder` **不封顶**（`MAX_FILES` 只校验 `files`），5000 份全归档；同一个文件夹**多带一张无关的 jpg** 就落进 `files` 清单，只处理前 2000 个。界面侧展开文件夹时才封顶 20000 个目录／20000 个文件。
- 递归展开遇到 junction／目录软链会绕：自指向的 junction 让 `Directory.EnumerateFiles(AllDirectories)` 一路转不完，所以 `EnumeratePdfs` 是自己写的逐层遍历，每个目录先按它的真实身份（`ResolveLinkTarget(returnFinalTarget: true)`，链接算它最终指向的地方）记账，走过的再遇到就跳过——自指向的环在这里断掉；同时封顶 20000 个目录／20000 个文件，超了带着已拿到的结果返回并在日志里说明截断。服务侧的整目录扫描同理，`find_pdfs` 也不用 `rglob` 了，直接不进目录链接——Windows 的 `os.scandir` 把 junction 当普通目录（`os.path.islink` 也答 `False`），只有 `entry.is_junction()` 认得它，不挡的话一张票会被数出 32 份。
- 「这批路径该怎么解释」放在 `Services\DropInbox.cs` 里，纯计算不碰控件，界面只把结果写进控件；它的分支由 `temp\dropinbox_test` 直接编译这份生产代码来验（33 条：单文件夹、散文件、混拖、只拖非 PDF、只拿到链接、空清单、重复拖，把归档目录连着别的文件夹一起拖／只拖归档副本两例（后者的提示必须说「都是归档目录里已有的副本」，不许写「没有 PDF」），零 PDF 文件夹两例，目录里带自指向 junction 一例（限 8 秒内必须收完且只收到一个 PDF），只拖一个 `icacls /deny` 拒读的文件夹一例（提示必须是「读不动」而不是「已选择拖入的文件夹」），长路径一例（343 字符的 PDF 要真收进清单，不再只要求「别说成没有 PDF」），正好 2000 个不砍／2001 个砍到 2000（断言留下的是用户亲手拖的那张散文件、少掉的是文件夹展开的其中一个，而不是只对文案做子串匹配）／只拖一个大文件夹仍走整目录扫描三例，文本兜底的分号列表/网页链接/空文本/重复路径四例，外加 `CollectPaths` 的逐项取路径六例（全好／中间一项抛／整批都抛／给空路径／一个项都没给／多项各抛各的时断言报的是**第一个**原因、不被后面覆盖），`MergeTextFallback` 五例（文本重复清单已有项、大小写不同、`file://` 形式、清单本来空、文本整段空白，最后一例走 `Plan`：同一个目录在两种格式里各出现一次时**仍按「只拖一个文件夹」处理**，不然早退就悄悄失效了）。junction 和 icacls 两例的夹具造不出来时**按失败计**，不然 README 写的条数会当场虚一条。服务侧那条整目录扫描用 `temp\junction_scan_probe.py` 现造一个自指向的 junction 当夹具验，断言一个 PDF 只被收一次。

- 拖放这条链路的接收端（`files` 协议、非 PDF 拒绝、多页归档）是照界面发出的报文直接打服务验的；**真正的鼠标拖拽要在本机手工试一次**——模拟 OLE 拖放需要往磁盘上写注入鼠标事件的脚本，这类脚本在本机一落地就被 Defender 清掉，自动化验不了。但「松手之后那段代码」现在有了运行时证据：`temp\paste_uia_check.ps1`（10 条）往剪贴板写 `CF_HDROP`/纯文本，用 UIA 点「粘贴文件」，驱动的是**同一个 `DataPackageView` 和同一条接收链**——两个 PDF 进清单、空清单时粘贴一个文件夹走「选目录」早退并且**紧接着点「开始分类」确认扫的就是那个目录**、已有清单时再粘贴同一目录是「本轮新增 0 个」、只给文本时兜底认出路径、给一段大白话时当场说「没有可认出的路径」、逐张粘贴累加、路径不存在（云端占位/复制完被删）时报的是「读不出来」而不是「没有 PDF」，最后把剪贴板恢复原样、界面关掉。
- 另一条更干净的路也试过，结论是走不通：另起进程造一个 CF_HDROP 数据对象调 `ole32!DoDragDrop`，再把自己的窗口一路贴着物理光标挪动，让系统的命中测试落在放置区上（探针确认了「落点归属本界面」）。但 OLE 的拖拽循环在没有真实鼠标键抬起的事件时**根本不会回头调用源的 `IDropSource`**（`QueryContinueDrag`/`GiveFeedback` 各 0 次），往自己线程的消息队列投 `WM_LBUTTONUP` 也不起作用，所以「松手落下」这一下只能由人做，那个探针工具已删掉，别再照旧思路试第二遍。
- 第三条也想试的路已经撞死过一次，记下来免得重复：从**进程外**把这次落下递出去——照 ole32 自己找放置目标的查法 `WindowFromPoint` → 逐级 `GetParent` + `GetProp(hwnd,"OleDropTargetInterface")`，再调 `IDropTarget::DragEnter/DragOver/Drop`。前半段是成立的（确实查到落点上挂着放置目标），后半段不行：`WindowFromPoint` 返回的是**最上层**窗口，界面被别的程序一盖就打到别人的窗口上；而 `GetProp` 回的那个指针只在**属主进程的地址空间**里有效，进程外拿它去 `Marshal.GetObjectForIUnknown` 是 `Fatal CLR error (0x80131506)`。ole32 能用它，是因为这套查找发生在目标进程内部。第三条路也堵死：在**进程内**自己去查那个属性——把本进程 7 个顶层窗口连子窗口共 10 个 HWND 全扫一遍，`OleDropTargetInterface`／`OleDropTarget` 两个属性都是空的，也就是 WinUI 3 的 OLE 接线不通过这条公开渠道暴露，微软那一段递不进去。于是探针改成一个能真验证的东西：`winui\Services\DropSelfTest.cs`（只在设了 `INVOICE_DROP_SELFTEST` 时执行，正常运行是死路）把**我们自己那段接线**的运行时状态写出来，由 `temp\drop_transport_check.ps1`（8 条）断言——`DropZone.AllowDrop=True`、`FolderPathBox.AllowDrop=True`、`PasteButton.IsEnabled=True`、清单从 0 项起步，以及 `WindowFromPoint(源目录框中心)` 命中的窗口 pid 等于本进程 pid（落点真的落在这个 XAML island 上，实测 `Microsoft.UI.Content.DesktopChildSiteBridge` → `WinUIDesktopWin32WindowClass`）。这几条正好盯住历史上真出过的那类回归：切页复用缓存页时 `AllowDrop` 停在 `false`，表象就是「拖不进去」。结论不变：**鼠标物理落下那一下只能人来做**，其余全链路都有运行时证据。
- 与之配套的两条兜底现在在生产代码里：`GetStorageItemsAsync` 挂起时 deferral 不再有上限的问题——`DropReadTimeout` 20 秒封顶，超时写清「这个来源 20 秒内没给出文件清单（多半是那张票还在下载、或云端占位还没落盘），这次先不收」并释放 deferral；另外 `ReadDroppedPathsAsync` 会区分「来源压根没给清单」和「来源**说**给了清单却一项都没渲染出来」，后者不再被错报成「只给了链接或缩略图，请先 Ctrl+C」。
- 结尾带点的文件名（`点结尾.pdf.`，Windows 认为它和 `点结尾.pdf` 是同一个文件、`File.Exists` 答 True，而 `PurePath.suffix` 对前者回空串）两侧口径一致：界面侧 `DropInbox.IsPdf` 先剥掉结尾的点再判后缀，服务侧 `classify_invoices` 那两处后缀判断同理。这种形态在资源管理器里造不出来（它会把结尾的点剥掉），所以 `temp\dotted_name_probe.py` 用原样通道 `\\?\` 直接写出来，再打活服务验 5 条：文件真造出来了、没被拒成「不是 PDF」、被正常归类、归档计数算进去了、与不带点的对照组归到同一类。
- 端到端还有一条把活界面 + 活服务 + 真票样串起来的验证：`temp\e2e_drop_check.ps1`（6 条）。票样先复制进自建夹具目录再用（归档产物不带原始文件名，断言也只回显计数与分类名，票面信息不外露），验的是「两张不同票种进清单 → 服务回包『已归档 2 个发票』→ 两种票各落进自己的分类目录 → 归档目录真的多出两份副本 → 处理的是拖入那一批而不是源目录 → **原件大小与两个时间戳一个都没变**」。它跑之前要把服务的 `INVOICE_OUT_DIR` 指到 `temp\service_out`，跑完记得 `-Default` 换回来。

- 设置页另有一条：`temp\settings_ledger_check.ps1` 用 UIA 点「测试连接」「连接推送」「保存」，断言 health 回包被显示、推送已连接、填了的项报「已保存」、**清空服务地址后保存要说「空着的没改」**（不能谎报已保存）、台账 404 不报成服务不可用，共 5 项。检测连接带 5 秒超时，不会因客户端那 20 分钟的扫描超时挂住。
- 界面侧的兜底：`App` 装了 `UnhandledException` 处理，异常写进 `%LocalAppData%\invoice_management_system\crash.log` 后让窗口继续活着；`MainWindow` 恢复上次页面失败会退回首页并改写 `last_page.txt`，不会卡在「一开就崩」；`WsClient` 的接收循环把处理器单独包了一层、收尾放进 `finally`，订阅者抛异常不会再静默带走循环。
- 实时日志的离页存活：推送钩子改成全进程挂一次、页面 `Unloaded` 时不再退订。原先退订会让「扫描进行中人切到别的页」这段时间零订阅者，日志是在**源头**丢的——服务只在检测不到订阅者时才把日志塞进 POST 响应兜底，而那一轮早就发出去了，回来补不回来。现在处理体按「活着的那一页」投递，没有活页时先写进进程级日志副本，回到这一页 `ReplayLog` 再倒出来。同一轮改动还让切页重建的那一页把上一轮结果补渲染出来，免得卡片停在「（0）」而日志写着「已归档 N 个」。验证：`temp\ws_offpage_check.ps1`（6 条）配 `temp\slow_push_service.py`（每秒推一条、共 6 条，把扫描窗口拉够长好在中途切页），断言离开期间推来的 4 条一条不丢、每条只记一遍、切走时那一页确实不在屏幕上、切回来卡片和日志对得上。
- 拖入清单的去重从两两比较改成按键集合：`DropInbox.Key`（`Normalize` 之后的形式）配 `HashSet`，散文件那批进来前先过 `Distinct`，文件夹展开的、文本兜底的、界面累加的都 O(1) 查。原先每比一次要做两回 `GetFullPath`，从文件夹一次拖两千个 PDF 是 O(n·m)，UI 线程被钉住几秒、看着就是「拖进去没反应」；顺带删掉了后面那遍只按原串比的线性去重（它既漏掉 `C:/a.pdf` 与 `C:\a.pdf` 是同一张票，又是白跑）。
- 拖进一个文件夹＝选目录那条写入不再被自己判成「用户改了源目录」：`TextChanged` 是晚一拍到的，原先用来挡它的同步布尔在它到达时早已复位，于是白 `++` 一次拖放代号（并发进行的另一次拖放会被判作废）。现在改成记值不记时刻——框里的文本等于界面刚写进去的那个值就消化掉这一次；同时把这个目录写进 `LocalStore` 的上次源目录，重启回到这一页不再是个空框。
- 扫描锁定是进程级的：`_scanning` 改成静态，扫描状态一变就广播给每个活着的页面实例，切页重建出来的那一页立刻显示「分类中…」、放置框同样禁用，也不会并发发起第二次扫描（服务侧 `_scan_lock` 会把两轮排开，但界面不该让人以为同时在扫两个目录）。
- `temp\nav_leak_check.ps1` 量过切页内存：来回切 96 次，私有字节增长约 19 MB，清不清后退栈、缓不缓存当前页都一样——所以这块增长不能算归因到后退栈；后退栈和多余的页面缓存该关还是关了（返回按钮本来就是关的），但这条测试脚本证明不了「修好了一个泄漏」，只证明增长与这两处无关。
- 扫描日志另存了一份进程级副本（上限 500 行）：中途切到别的页会重建一个发票识别页，回到本页时把副本倒回去，不会只剩一片空白；同一轮结果用代号（generation）判重，POST 响应和 WebSocket 的 `done` 推送只会渲染一次，切页后回来的那个实例则靠 `done` 推送补上结果。
- HTTP 那条 `Timeout` 是 20 分钟，定这个数有实测依据：本机扫 60 份真实票样 5.6 秒（约 94 ms/份），单次上限 2000 份的满批约 3 分钟，留几倍余量给多页大票表。即便如此，超了也不等于扫描失败：服务那边线程还在跑，跑完照样从 `/ws` 推 `done`，界面收到就渲染。所以这条路径的日志写的是「等响应超时了，但服务可能还在后台跑：先看下面的日志或归档目录，别急着再点一次」，而不是「本地服务无响应」——后者会让人以为没成功，接着再点一次，把同一批票重复归档一遍（重名会追加，不会覆盖，但结果是双份）。
- 满批（2000 个文件）会把这三处推到极限，都改了：① 日志不再一行行 `LogBox.Text +=`（每行整串重拷）加每行一次 `UpdateLayout()`，而是攒进一个队列、每个 UI 回合只刷一次，显示端也留上限；② `WsClient` 原来按 8192 字节分帧 `Encoding.UTF8.GetString`，几千条明细的中文报文里一个汉字被拆在两帧时各自补出 U+FFFD，严重时 JSON 直接解析失败、这一轮唯一的渲染机会就没了，现在换成一个跨帧保留状态的 `Decoder`；③ 切页留下的旧实例也订阅着同一个推送事件，同一条 `done` 会被处理好几遍，现在按同一次回调的对象标识只认一次。
- `done` 推送和点击次数按序号配对：服务是串行跑扫描的，推送按点击顺序到达，所以序号比点击次数小的那个一定是「上一轮（响应早超时）补到的」——只往日志里补一行归档了几个，不去占最新一轮的渲染槽。不加这条的话，超时后再点一次，上一批的结果会把卡片和计数占满，真正这一批的结果反倒被判「已渲染」。POST 正常走完（除超时外的所有出口）会把两个序号对齐，免得到下一轮被误判。
- 上次扫过的源目录会回填到源目录框（`source_folder`），不用每次重选。
- `ApiClient` 遇到非 2xx 会抛 `ApiStatusException`（带状态码），台账页据此把「端点还没实现（404/501）」和「本地服务不可用」分开报，不会再拿 404 报成服务挂了。
- **不加 `-p:WindowsPackageType=None` 那组参数直接跑 exe 会崩**（`0x80040154 REGDB_E_CLASSNOTREG`，即 Windows App Runtime 未安装）；要么按上面自包含，要么装 `Microsoft.WindowsAppRuntime` 运行时。
- 本机 PATH 里的 `dotnet` 是 `C:\Program Files (x86)\dotnet`（没有 SDK），要用 `C:\Program Files\dotnet\dotnet.exe`，或 VS 里的「.NET 桌面开发」。
- shell 里的 `HTTP_PROXY/HTTPS_PROXY` 指向 127.0.0.1:7897 时，代理一挂 `dotnet restore` 就报 NU1301 SSL 失败；把这两个环境变量清掉即可直连 nuget.org（VS 走系统代理，与环境变量无关）。
- 台账页、首页的统计卡片还是占位，数据要等 SQLite（need.md 五）落地。
